## Mainnets

A server with `KITE_IS_TESTNET` unset or `false` offers the mainnets in the server's [chain registry](https://github.com/Kite-01/server/blob/main/src/shared/chains/registry.ts). Each needs your own [Kite factory](/contracts/overview#deploying-a-factory) deployed on it before it can be configured.

## Deploying

Kite is one process and a Postgres database. The published image is the simplest way to run it:

```sh
docker run -d --restart unless-stopped -p 3000:3000 --env-file .env ghcr.io/kite-01/server:latest
```

Pin a `sha-<sha>` tag rather than `latest` to choose when you upgrade. To build the image yourself, `docker build -t kite-server .` in the [server repository](https://github.com/Kite-01/server).

Put it behind a reverse proxy or load balancer that terminates HTTPS, and set `KITE_PUBLIC_BASE_URL` to the public HTTPS URL. Use a managed Postgres, or one you back up. A managed one usually needs [TLS and smaller connection pools](/server/configuration#managed-postgres).

Background work, such as settling transfers and delivering webhooks, runs in the same process on a queue kept in Postgres, so there's nothing else to run.

### Reverse proxy

A payment link's [x402](/payments/x402) response carries every offer in its `PAYMENT-REQUIRED` header, base64-encoded: about 300 bytes for each chain the app accepts. Proxies cap the size of a response's headers, and past that cap they answer `502 Bad Gateway` in place of the `402`, while the checkout page and the rest of the API keep working.

<Tabs>

<Tab title="nginx">

nginx reads a response's headers into a 4 KB buffer by default, which a payment link outgrows at about 11 chains. nginx then logs `upstream sent too big header while reading response header from upstream`. Raise the buffer where you proxy to Kite:

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_buffer_size 16k;
    proxy_buffers 8 16k;
    proxy_busy_buffers_size 32k;
}
```

16 KB is room for about 40 chains. `proxy_busy_buffers_size` must be at least `proxy_buffer_size`, or nginx won't start.

</Tab>

<Tab title="Apache">

Apache's `mod_proxy` caps each response header line at 8,192 bytes, which a payment link outgrows at about 22 chains. Apache then logs `AH10124: header size is over the limit allowed by ResponseFieldSize`. Raise it on the `ProxyPass` line, with Apache 2.4.53 or newer:

```apache
ProxyPass        / http://127.0.0.1:3000/ responsefieldsize=65536
ProxyPassReverse / http://127.0.0.1:3000/
```

</Tab>

</Tabs>

To check, request a payment link as JSON: it should answer `402`, not `502`.

```sh
curl -s -o /dev/null -w "%{http_code}\n" -H "Accept: application/json" https://your-server.example/pay/<payment-link-id>
```

If you redirect another domain to Kite, redirect straight to its `https://` URL, so a client never repeats a request carrying a signed payment over plain HTTP.

## Checklist

- [ ] Strong, unique `KITE_ROOT_KEY` and `KITE_ENCRYPTION_KEY`, kept in a secret manager.
- [ ] A reverse proxy whose header limits fit a payment link's [x402 response](#reverse-proxy).
- [ ] A dedicated operator mnemonic, set as the operator of your Kite factory on each chain.
- [ ] Your own RPC URLs on each chain.
- [ ] A deposit notifier on each chain that has one, and `KITE_PUBLIC_BASE_URL` reachable from the internet.
- [ ] A gas sponsor on each chain, or native tokens in the operator wallet where there's none.
- [ ] An address you control for every chain each app accepts.
- [ ] Apps use [API keys](/authentication/api-keys) with only the scopes they need, never the root key.
- [ ] [Webhooks](/integrate/webhooks) verified with their signing secret.
- [ ] `KITE_ENABLE_DASHBOARD=false` if nobody should reach the dashboard from this URL. The checkout stays up.

## Upgrading

With Docker, pull the new image and restart: it applies migrations as it starts.

```sh
docker compose pull && docker compose up -d
```

From source, pull the code and run the migrations yourself first:

```sh
git pull
bun install && bun install --cwd client
bun run migrate
bun run build
bun run start
```

<Warning>

Always use `bun run migrate`. Some releases need data upgrades that it runs after the schema migrations.

</Warning>

## Backups

Back up the database and keep `KITE_ENCRYPTION_KEY` with it: without the key, the provider keys and webhook secrets in a backup can't be read. Funds are never in the database. They're on-chain, in each transfer's contract until it settles or refunds.

## Monitoring

- `GET /api/overview/info` with the root key answers when the server and database are up.
- Watch your gas sponsor's balance or policy limits, or the operator wallet's balance on chains without a sponsor, so settlements don't stall.
- Failed webhook deliveries are listed on each webhook in the dashboard.
